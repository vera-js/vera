as attributes

A scroll runtime with no build step and no dependencies. Everything on this page is driven by data-vm-* attributes — no animation code was written for it.

Presets

The shortest path. A name on the marker attribute expands into ordinary keyframes, so a preset is never a special case — it produces exactly what writing the attributes by hand would.

fade-up
Rises 40px while fading in.
fade-left
Drifts in from the right.
zoom-in
Scales up from 0.8.
blur-in
Resolves from 12px of blur.
<div data-vm="fade-up">

Keyframes

A keyframe is a position and a value, and one attribute holds as many as you like. This plate overshoots left, swings back past centre, then settles — four keyframes in one attribute. 

<div data-vm
  data-vm-translate-x="0% -90px, 35% 45px, 65% -22px, 100% 0px"
  data-vm-rotate="0% -8deg, 100% 0deg"
  data-vm-opacity="0% 0, 30% 1">

The old design capped out at two midpoints and spent a whole attribute on each one. A property is now a single attribute, and a keyframe is a position and a value.

Several properties at once

Transform, filter and border radius on one element. Each category is composed into a single style write per frame, in a fixed order — CSS transform functions don't commute, so the order is defined by the schema rather than by the order you happened to write the attributes. 

<div data-vm
  data-vm-translate-y="0% 70px, 100% 0px"
  data-vm-scale="0% 0.86, 100% 1"
  data-vm-rotate="0% -5deg, 100% 0deg"
  data-vm-blur="0% 14px, 100% 0px"
  data-vm-opacity="0% 0, 45% 1"
  data-vm-radius-top-left="0% 90px, 100% 14px">

A bare value is the end of the timeline, so the whole of a fade-in is data-vm-opacity="0".

Shaping the curve

data-vm-ease reshapes how value relates to scroll position — the CSS timing vocabulary, evaluated per segment the way @keyframes does. It is a wired module (@verajs/motion/easings), because linear is the default and most pages never leave it. All three lanes below travel the same distance over the same scroll; only the shape differs.

linear — the default
ease-in-out
cubic-bezier(0.34, 1.56, 0.64, 1) — overshoots 
<div data-vm data-vm-ease="cubic-bezier(0.34, 1.56, 0.64, 1)"
  data-vm-translate-x="0% 0vw, 100% 55vw">

Staggering a row

Siblings at the same height share a scroll window, so a row animates in perfect unison. That is right for a hero and wrong for a list. Here is the same cascade written both ways.

By hand — shift every keyframe on every child

<div class="tiles">
  <div data-vm data-vm-translate-y="0% 70px, 60% 0px">
  <div data-vm data-vm-translate-y="12% 70px, 72% 0px">
  <div data-vm data-vm-translate-y="24% 70px, 84% 0px">
  <div data-vm data-vm-translate-y="36% 70px, 96% 0px">

With data-vm-stagger — one attribute on the parent

<div class="tiles" data-vm-stagger="12">
  <div data-vm data-vm-translate-y="0% 70px, 60% 0px">
  <div data-vm data-vm-translate-y="0% 70px, 60% 0px">
  <div data-vm data-vm-translate-y="0% 70px, 60% 0px">
  <div data-vm data-vm-translate-y="0% 70px, 60% 0px">

Identical motion. Every child is now the same markup, so the row can be generated from a loop and the cascade is one number to tune. % by default; any position unit works, and a negative step runs the row in reverse.

Splitting text

data-vm-split breaks a block of plain text into pieces — words, characters or layout-measured lines — and moves the animation attributes onto each piece. The container keeps stagger, so a cascade is the feature that already exists. A screen reader sees the original sentence, not the pieces.

Every word in this sentence arrives on its own scroll window.
<div data-vm-split="words" data-vm-stagger="3"
  data-vm-translate-y="0% 30px, 55% 0px"
  data-vm-opacity="0% 0, 55% 1">Every word in this sentence…</div>

Wired from @verajs/motion/split. Lines re-group themselves when the text re-wraps — resize this window and the grouping follows the layout.

Colour, gradients and shadows

The runtime never learns what a colour is. @verajs/motion/paint gives each authored value a slot, the curve steps between slots, and the CSS transition that carries inertia does the blending — the engine interpolates colour correctly across every colour space, which no hand-written parser should try to match.

This card is repainting as you scroll. Background, text colour and box-shadow are three attributes. Each keyframe is any value the engine accepts — CSS.supports() is the parser. 
<div data-vm
  data-vm-background="0% #16161b, 45% #1c3a2c, 100% #1b2a4a"
  data-vm-color="0% #8b8b98, 100% #dbe7ff"
  data-vm-shadow="0% 0 0 0 rgba(0,0,0,0), 100% 0 24px 64px rgba(110,168,254,0.25)">

And when a value should morph rather than step, put its parameters on the number line instead. This gradient is one line of CSS reading three custom properties — hue, centre x, centre y — and a module of three PropertyDefs animates the numbers. Registered with @property, the inertia transition interpolates them like any transform: a continuous sweep from green to purple while the circle drifts, no colour parser anywhere.

This gradient is morphing as you scroll. Green to purple through every hue between, the engine doing the colour math in oklch — the runtime only ever wrote three numbers.

A module can also write something that is not a style at all. This one toggles a class at a scroll position — discrete: true, because a class is on or off and there is no half a class — and the page's own CSS transition does the rest. It is the shape to copy when the effect you want is already written in your stylesheet.

This card is switched on by a class. No inline style does this: at 55% of the timeline the module adds is-lit, and every property that class changes transitions in CSS. Scroll back and it switches off again. 
const classes = [
  { attribute: 'lit', category: 'class', defaultUnit: '', units: [''], initial: 0,
    discrete: true,
    apply(node, value) { node.classList.toggle('is-lit', Math.round(value) >= 1); } },
  { on: 'release',  fn: (node) => node.classList.remove('is-lit') },
  { on: 'teardown', fn: (owns) => { /* remove it from every element this instance owns */ } },
];

<div data-vm data-vm-lit="0% 0, 55% 1">

The two lifecycle entries are the part worth copying. Core owns the inline styles it composes and hands them back on destroy() — it knows nothing about your class. A module that touches anything else owes the page an undo, and owns is what keeps one instance's teardown from stripping classes off another instance's elements. 

const gradient = [
  { attribute: 'gradient-hue', category: 'gradient', cssProperty: '--gradient-h', defaultUnit: '', units: [''], initial: 155 },
  { attribute: 'gradient-x',   category: 'gradient', cssProperty: '--gradient-x', defaultUnit: '%', units: ['%'], initial: 30 },
  { attribute: 'gradient-y',   category: 'gradient', cssProperty: '--gradient-y', defaultUnit: '%', units: ['%'], initial: 35 },
];
wireMotion([gradient]);

<div data-vm
  data-vm-gradient-hue="0% 155, 100% 310"
  data-vm-gradient-x="0% 25%, 100% 72%"
  data-vm-gradient-y="0% 30%, 100% 68%">

Late layout

These three images carry no width or height, on purpose. Until each one loads, the browser reserves no space for it, so everything below shifts down as they arrive — and every position measured at startup goes stale.

Geometry is cached rather than re-read per frame, so a runtime that measures once and trusts it forever would animate these against positions that no longer exist. Measured on a repro page with throttled images, the drift reached 1451px. A load listener and a ResizeObserver re-measure when the page settles.

Triggering on state, not scroll

data-vm-when takes a selector. While the element matches it, the animation sits at its end; while it does not, at its start. It replaces the scroll driver rather than adding to it — everything else is identical, including the damping, which is what makes it ease rather than snap.

Plain CSS does the simple version of this in three lines and you should use it when it fits. This earns its place when the element is also scroll-animated (inline transforms beat class rules), when there are several properties and keyframes to coordinate, or when reaching for a stylesheet is the thing you are trying to avoid.

No scroll involved. The class is toggled by the button; the runtime notices and moves the animation to its other end. 
<div data-vm data-vm-when=".is-open"
  data-vm-translate-y="0% -14px, 100% 0px"
  data-vm-scale="0% 0.96, 100% 1"
  data-vm-opacity="0% 0.25, 100% 1">

Pinning

data-vm-pin holds an element against the viewport while its animation runs, then releases it back into the flow. It is position: sticky underneath, so the element never leaves layout — nothing jumps when it attaches and nothing collapses when it lets go.

pinned at 15vh · growing · then released
<div data-vm data-vm-pin="15vh"
  data-vm-scale="0% 0.82, 70% 1.06">

Following a path

Point an element at an SVG <path> and it travels along it as you scroll. The shape is handed to offset-path once at startup; the animation itself is offset-distance, an ordinary animatable percentage — so it runs on the compositor and the inertia setting damps it like anything else.

One thing to know: offset-path reads the path's coordinates as CSS pixels and does not scale them. A responsive SVG would draw one curve while the element travelled along a differently-sized one, so the guide below is rendered at exactly its viewBox size. 

<path id="route" d="M 20 210 C 140 20 …"/>

<div data-vm
  data-vm-path-selector="#route"
  data-vm-path="0% 0, 100% 100">

Scrubbing an image sequence

A <canvas> whose frame is chosen by scroll position — the technique behind product-page hero animations. 48 frames here; real ones run to several hundred.

Frames load in a sliding window around the current position, a few at a time, and nothing is allocated while drawing. The pre-rewrite version requested the whole sequence at once — 300 simultaneous connections on page load — and built a new Image every frame it drew. The module is wired, not fetched on demand — being synchronous is what removed a whole class of in-flight bug — and a page that does not wire it pays nothing for it. 

<canvas data-vm
  data-vm-frame="0% 0, 100% 47"
  data-vm-frame-url="./img/seq/" data-vm-frame-count="48"
  data-vm-inertia="0">   <!-- exact tracking, no inertia -->

Inside a web component

querySelectorAll cannot reach into a shadow root, so roots are registered explicitly. This card is rendered by a VeraJS component; clicking its button forces a re-render, and the animation survives it.
